# Chapter 3. AI와 함께하는 개발 방법론


## 3.1 왜 설계가 중요한가

### AI 시대의 역설 (바이브 코딩 숙취)
코드 생성이 쉬워질수록 설계는 오히려 더 중요해진다.  
AI는 **어떻게(How)** 구현할지는 알지만, **무엇을(What)** 만들어야 하는지는 모른다.

### 설계 없는 개발의 위험성
요구사항이 구체화될수록 대규모 재작성이 불가피하다.

| 일차 | 상황 | 결과 |
|---|---|---|
| 1일차 | 개인용 웹 앱 CRUD | 생성 |
| 3일차 | 팀 공유 기능 추가 | 인증/권한 시스템 급조 |
| 7일차 | SaaS로 서비스 | 멀티테넌시 구조 전면 재작성 |
| 14일차 | 온프레미스 옵션 | 환경 설정 시스템 재설계 |

### 설계의 실용적 범위 (3가지)
- **요구사항 분석**: 핵심/비기능 요구사항 수립
- **아키텍처 결정**: 기술 스택, 구조 결정
- **인터페이스 정의**: API 규격, 시스템 간 호출 방식

### 핵심 원칙: Garbage In, Garbage Out
AI는 나쁜 입력도 그럴듯한 출력(할루시네이션)으로 만든다.  
명확한 마크다운 명세 문서가 필수다.

## 3.2 작은 단위로 쪼개기의 힘

### 다중 AI 에이전트 활용 전략
단일 에이전트 의존 시 학습 데이터 편향과 Context Lock-in 위험이 있으므로 교차 검증이 필요하다.

| 단계 | 도구 | 목적 |
|---|---|---|
| 1단계 아이디어 정리 | Gemini (무료) | 고려 요소 도출 |
| 2단계 설계 문서 초안 | Gemini (무료) | REQUIREMENTS.md 작성 |
| 3단계 설계 검토/확정 | Claude (최소 토큰) | 누락 기능 점검 |
| 4단계 구현 | Claude Code (주 비용) | REQUIREMENTS.md 기반 구현 |

**핵심:** 비용이 가장 많이 드는 구현 단계 전에 설계를 확정한다. 설계가 흔들리면 토큰 낭비가 그대로 비용으로 이어진다.

### 점진적 설계 (Progressive Design)

| 설계 단계 | 시점 | 주요 결정 사항 | 변경 비용 |
|---|---|---|---|
| 1차 설계 | 프로젝트 시작 전 (필수) | 배포 형태, 기술 스택, 인증 방식 | **매우 높음** (거의 재시작) |
| 2차 설계 | 1주차 구현 중 | API 엔드포인트, DB 스키마, 에러 코드 체계 | 중간 |
| 3차 설계 | 2주차 통합 전 | 프런트엔드 컴포넌트 구조, 상태 관리, API 응답 표준화 | 낮음 |

## 3.2.1 한 번에 하나의 작업만 요청하기

**가장 흔한 실수: 복합 요청**  
"그리고", "또한", "추가로" 같은 단어가 프롬프트에 나오면 작업을 분리해야 한다는 신호다.

복합 요청 시 발생하는 문제:
- 기능/코드 품질 저하
- 복합 에러로 인한 디버깅 어려움
- 기능 간 컨텍스트 침범 및 혼란

### ❌ 나쁜 예
```
"사용자 인증 시스템 만들어줘. 회원가입, 로그인, 로그아웃,
비밀번호 변경, 이메일 인증까지 포함해서."
```
→ 대량 파일 생성/수정, 버그 불가피, 어디서부터 검증할지 막막

### ✅ 좋은 예 — 단계별 분해 + 즉시 검증

| 요청 | 작업 내용 | 검증 방법 |
|---|---|---|
| 1 | User 모델 스키마 정의 | 요구사항 대조 확인 |
| 2 | 회원가입 API (POST /register) | Postman 테스트 |
| 3 | bcrypt 비밀번호 해싱 | DB 저장값 확인 |
| 4 | 로그인 API (POST /login) | 자격증명 테스트 |
| 5 | JWT 토큰 생성 로직 | 토큰 유효성 확인 |
| 6 | 인증 미들웨어 | 미들웨어 단독 테스트 |
| 7 | 보호된 라우트에 미들웨어 적용 | 401 에러 + 통합 테스트 |

**핵심:** 작업 단위가 작을수록 → 검증이 쉽고 → 문제 지점이 명확하고 → 피드백이 빠르다.

## 3.2.2 작업 분해의 기준과 단위

### 적절한 작업 크기 판단 기준 4가지

| 기준 | 설명 | 예시 |
|---|---|---|
| 단일 책임 원칙 | 하나의 요청 = 하나의 책임 | "사용자 생성"과 "이메일 발송"은 별도 요청 |
| 테스트 가능 단위 | "이 기능이 동작하는가?" 예/아니오로 답 가능한 크기 | 독립적으로 검증 가능해야 함 |
| 10분 내 검증 | 출력 확인 + 코드 리뷰 + 테스트 실행이 10분 초과 시 더 쪼개야 함 | 경험적 기준 |
| 파일/기능 경계 | 같은 도메인이라도 경계와 역할이 다르면 분리 | 로그인/로그아웃은 같은 파일, 회원가입/수정은 별도 파일 |

### 컨텍스트 윈도우 한계 관리

```
컨텍스트 한계 징후
├── AI 응답이 반복됨
└── 이전 대화 내용을 반영 못함
    └── → /clear 명령으로 새 세션 시작
```

**작업 크기 결정의 핵심 관점:** "실패하면 얼마나 손해인가?"  
요청이 클수록 실패 시 토큰 손실 + 시간 소모가 비례해서 커진다.

## 3.3 명확한 지시의 기술

**핵심 원칙:** "무엇을 요청하는가"보다 **"어떻게 요청하는가"** 가 더 중요하다.  
모호한 지시 → 여러 번 수정 반복보다, 명확한 지시 한 번이 시간과 토큰 모두 절약된다.

---

## 3.3.1 컨텍스트 제한의 원칙

정보는 많을수록 좋은 게 아니다. **필요한 정보만 정확하게** 전달해야 한다.

| 요소 | 질문 | 역할 |
|---|---|---|
| 목표 (What) | 무엇을 달성해야 하는가? | 작업 방향 설정 |
| 맥락 (Context) | 현재 상황과 배경은? | AI가 올바른 가정을 하도록 유도 |
| 제약 조건 (Constraints) | 지켜야 할 규칙은? | 범위 제한, 일탈 방지 |
| 완료 조건 (Done Criteria) | 성공을 어떻게 판단하는가? | 명확한 종료 지점 제시 |
| 예시 (Examples) | 기대 결과의 구체적 모습은? | 모호함 제거 |

**추가 테크닉**
- **Few-shot:** 기존 작업 샘플이나 스펙을 직접 제공하면 훨씬 정확한 코드 생성
- **패턴 참조:** `"@blog.controller.ts의 패턴을 따라서"` 처럼 기존 코드 스타일을 명시
- **변경사항 관리:** 설계/기능 변경 시 `CLAUDE.md` 또는 `REQUIREMENTS.md`에 변경 이력 기록

## 3.3.2 완료 조건을 명시하는 방법

완료 조건이 없으면 AI 스스로 판단해서 완료 처리 → 기대와 다른 결과 → 꼬리물기 프롬프트 반복의 악순환이 된다.

**좋은 완료 조건의 3가지 요건:** 구체적 + 측정 가능 + 검증 가능

| 나쁜 조건 | 문제점 | 좋은 조건 |
|---|---|---|
| "빠르게 동작해야 함" | 기준 불명확 | "API 응답 300ms 이내" |
| "에러 처리가 잘 되어야 함" | "잘"의 기준 없음 | "에러 시 재시도 3회 후 에러 메시지 표시" |
| "코드가 깔끔해야 함" | 주관적 | "함수당 30줄 이내, 중복 코드 없음" |
| "테스트가 필요함" | 범위 불명확 | "정상/실패/경계 케이스 각 1개 이상" |
| "잘 동작해야 함" | 완전히 모호 | "명세의 모든 시나리오 통과" |

**권장 워크플로:**
```
프롬프트 작성
└── 실행 모드 바로 진입 (❌)
└── Plan 모드로 완료 조건 분석 먼저 (✅)
    └── 계획 확인 후 실행
        └── 시행착오 방지 + 토큰 절약
```

## 3.4 매 단계 리뷰하기: 주의 깊은 수정의 원칙

### 왜 매 단계 리뷰가 필요한가

| 이유 | 핵심 내용 |
|---|---|
| 오류 누적 방지 | 초기 작은 문제 → 전체 구조적 문제로 확대 (기술 부채의 복리 효과) |
| 방향 수정 비용 최소화 | 변경 비용은 프로젝트 진행될수록 기하급수적 증가. 5개 작업 연쇄 후 첫 번째 문제 발견 시 5개 모두 수정 필요 |
| 학습 기회 | 리뷰를 통해 개발자의 코드 판단 능력(Taste) 성장 |

## 3.4.1 리뷰해야 할 것들

### 1. 요구사항 충족 여부
- 요청한 기능이 모두 포함되었는가?
- 요청하지 않은 기능이 추가되지 않았는가?
- 엣지케이스/예외 처리가 적절한가?
- 입출력 형식이 예상과 일치하는가?

### 2. 코드 품질 — 가독성 / 일관성 / 효율성 / 안전성

유용한 커맨드:
```bash
/review          # PR 리뷰 수준 점검 (커밋·PR 전)
/simplify        # 코드 재사용 및 품질 검토
/security-review # 보안 취약점 분석 (보안 민감 코드 작업 후)
```

### 3. 의도치 않은 변경 — 특히 주의할 것들
- 요청하지 않은 파일 수정
- 기존 테스트 삭제/비활성화 (**가장 경계해야 함**)
- 설정 파일/환경 변수 변경
- 의존성 추가/삭제
- 기존 함수 시그니처 변경

## 3.4.2 단계별 리뷰 습관

| 습관 | 내용 |
|---|---|
| 작은 작업 = 작은 리뷰 | 500줄 한 번보다 50줄 10번이 훨씬 효과적 |
| 승인 전 실행 | 문법이 맞아도 논리가 틀릴 수 있음. 반드시 실행 검증 |
| 테스트 먼저 | 기존 테스트 통과 확인 후 다음 작업으로 진행 |
| 질문하기 | 이해 안 되는 부분은 AI에게 설명 요청 → AI가 스스로 문제를 인식하기도 함 |

## 3.4.3 리뷰 워크플로와 되돌리기

```
작은 작업 요청
  → AI 결과물 수령
    → 코드 리뷰 (요구사항 / 품질 / 의도치 않은 변경)
      → 테스트 실행
        ├── 문제 발견 시 → 수정 요청 or git revert / /rewind
        └── 통과 시 → 커밋 → 다음 작업
```

### 되돌리기 전략 3가지

| 전략 | 내용 |
|---|---|
| 잦은 커밋 | 10분 단위 커밋. `git reset --hard HEAD~1`로 정확한 지점 복구 |
| 명확한 커밋 메시지 | `[AI] feat: 로그인 API 구현` 형식. AI 작성 코드 식별 가능하게 |
| 브랜치 전략 | 실험적 작업/대규모 리팩터링은 반드시 별도 브랜치에서 |

### 커밋 타입 prefix

| 타입 | 용도 |
|---|---|
| `feat` | 새 기능 |
| `fix` | 버그 수정 |
| `debug` | 디버깅 |
| `refactor` | 리팩터링 |
| `db` | 데이터베이스 변경 |
| `api` | API 엔드포인트 추가/수정 |
| `ui` | 프런트엔드 UI 변경 |
| `test` | 테스트 코드 추가/수정 |
| `docs` | 문서, 주석 추가/수정 |

> **마인드셋:** 되돌리기는 패배가 아니라 전략적 선택이다. `/rewind` 커맨드로 컨텍스트와 대화까지 함께 롤백 가능.

## 3.5 AI에게 없는 것 — 개발자의 판단력(Taste)

### Taste란?
기술적 판단력 + 미적 감각. 좋은 코드와 나쁜 코드를 구분하는 능력으로, 수년간의 경험을 통해 축적된다.

### 작동하는 코드 vs 좋은 코드

```typescript
// ❌ AI 생성 (작동은 함)
function filterTodos(todos, filter) {
  if (filter === 'all') return todos;
  else if (filter === 'active') return todos.filter(t => !t.completed);
  else if (filter === 'completed') return todos.filter(t => t.completed);
  else return todos;
}

// ✅ 개발자 개선 (타입 안전 + 확장성 + 의도 명확)
const filterStrategies: Record<FilterType, (todo: Todo) => boolean> = {
  all: () => true,
  active: (todo) => !todo.completed,
  completed: (todo) => todo.completed,
};
function filterTodos(todos: Todo[], filter: FilterType): Todo[] {
  return todos.filter(filterStrategies[filter]);
}
```

### AI가 대체할 수 없는 3가지 영역

| 영역 | 설명 |
|---|---|
| 트레이드오프 결정 | 성능/유연성/보안/비용 사이의 균형. 맥락을 아는 개발자만 가능 |
| 비즈니스 맥락 이해 | "왜 이 기능이 중요한가", "사용자가 어떻게 쓰는가"는 코드만으로 알 수 없음 |
| YAGNI 원칙 적용 | AI는 '더 완전한' 코드를 만들려는 경향. "지금 당장 필요하지 않은 것은 만들지 않는다" 판단은 개발자 몫 |

> **결론:** 코드에 대한 최종 책임은 언제나 개발자에게 있다.

## 3.6.1 증강코딩: AI 시대의 새로운 개발 방식

### 바이브 코딩 vs 증강코딩

| 구분 | 바이브 코딩 | 증강코딩 |
|---|---|---|
| 관심사 | 시스템 동작만 | 코드 품질 + 복잡도 + 테스트 + 커버리지 |
| 에러 대응 | 에러 메시지를 AI에게 던짐 | 원인 분석 후 단계적 해결 |
| 코드 기준 | 어떻게든 동작하면 OK | 손으로 작성할 때와 동일한 가치 체계 유지 |

### AI 궤도 이탈 3가지 경고 신호 (켄트 벡)

| 신호 | 설명 |
|---|---|
| 루프 (Loops) | 같은 문제를 다른 방식으로 반복. 실질적 진전 없음 |
| 요청하지 않은 기능 추가 | 통제 안 되면 복잡성 급증 |
| 치팅 징후 | 테스트를 통과시키기 위해 테스트 자체를 삭제/비활성화 (**가장 위험**) |

### Make it work → Make it right → Make it fast
작고 검증 가능한 단계로 반복. 문제 발생 시 즉시 되돌리기.

## 3.6.2 AI 출력의 비결정적 특성과 TDD

**테스트 = AI 비결정성에 대응하는 결정적 검문소**  
AI가 어떤 방식으로 구현하든, 테스트 통과 여부가 요구사항 충족의 객관적 기준이 된다.

### 테스트를 명세로 활용

```typescript
// 자연어 명세보다 정확한 실행 가능한 명세
describe('TodoList', () => {
  it('새로운 할 일을 추가하면 목록에 나타난다', () => {
    const todoList = new TodoList();
    todoList.addTodo({ title: '우유 사기', priority: 'high' });
    expect(todoList.items).toHaveLength(1);
    expect(todoList.items[0].completed).toBe(false);
  });
});
```

### Hook으로 자동 테스트 실행 (회귀 방지)

```json
{
  "hooks": {
    "PostToolUse": [{
      "matcher": "Edit:*.ts|Write:*.ts",
      "hooks": [{
        "type": "command",
        "command": "npm test -- --findRelatedTests $CLAUDE_FILE_PATH"
      }]
    }]
  }
}
```

## 3.6.3 AI가 TDD 사이클을 무시할 때 대응법

### AI의 TDD 위반 패턴 3가지
- 테스트 없이 구현 먼저 → "나중에 추가 가능"으로 마무리
- 테스트와 구현 동시 생성 → Red 단계 없어 테스트 유효성 검증 불가
- 구현 어려워지면 테스트 skip 또는 expect 조건 느슨하게 변경

### 명시적 단계별 지시 — 슬래시 커맨드 활용

```bash
/tdd-red  이메일 검증 함수   # 실패하는 테스트만 작성 (구현 금지)
/tdd-green                   # 최소한의 코드로 통과 (하드코딩 허용)
/tdd-refactor                # 테스트 유지하며 코드 개선
```

### CLAUDE.md TDD 금지 사항

```
❌ 테스트 없이 구현 코드 작성
❌ 테스트와 구현 동시 작성
❌ 테스트 skip / 주석 처리
❌ expect 조건 느슨하게 변경
```

## 3.6.4 AI가 만드는 회귀 방지하기

**AI 회귀 주요 패턴:** 기존 코드 무시 후 재작성 / 관련 없는 파일 수정 / 테스트 삭제

> CodeRabbit 2025 연구: AI 포함 PR은 인간 작성 코드보다 **1.4~1.7배** 더 많은 심각한 문제 포함

### 회귀 방지 전략

| 전략 | 내용 |
|---|---|
| 변경 전후 테스트 실행 | 수정 요청 전 전체 테스트 통과 확인 필수 |
| CI/CD 파이프라인 | AI 생성 코드도 예외 없이 자동화 테스트 통과 필수 |
| 커버리지 모니터링 | 새 코드에는 반드시 새 테스트 동반 |
| 회귀 테스트 스위트 | 핵심 기능은 별도 안전망으로 관리 |

---

## 3.6.5 테스트가 진짜 안전망이 되려면

### 좋은 테스트의 4가지 특성
- **행위를 테스트** (구현 세부사항 X)
- **실패 이유가 명확**
- **독립적** (다른 테스트에 영향받지 않음)
- **반복 가능** (언제나 동일한 결과)

### AI 생성 코드의 공통 취약점 (Augment Code 2025)
Happy Path에서는 잘 동작하지만, null 체크 / 조기 반환 / 가드 절 / 예외 처리가 자주 누락됨  
→ **경계 조건 테스트 필수**

### AI에게 테스트 리뷰 요청 항목
```
1. 놓친 경계 조건
2. 구현 세부사항 의존 여부
3. 실패 시 디버깅 용이성
4. 중복 제거 가능 여부
```

> **결론:** AI 시대에 TDD의 가치는 줄어든 것이 아니라 오히려 더 커졌다.

## 3.7 클로드 코드에서 MCP 설정하기

**MCP(Model Context Protocol)란?**  
AI가 외부 도구·데이터 소스에 접근하는 표준화된 프로토콜.  
Jira, Confluence, Slack, Sentry 등 외부 서비스와 연동하여 워크플로를 자동화한다.

---

## 3.7.1 MCP 서버 연결 방법 3가지

| 방식 | 특징 | 예시 |
|---|---|---|
| HTTP 서버 연결 | 클라우드 실행, 로컬 리소스 불필요 | `claude mcp add --transport http` |
| Stdio 서버 연결 | 로컬 프로세스 실행, 오프라인 가능 | `claude mcp add --transport stdio -- npx` |
| JSON 설정 추가 | 복잡한 설정·팀 공유, `.mcp.json`으로 버전 관리 | `claude mcp add-json` |

### Scope(적용 범위) 3단계

| Scope | 저장 위치 | 용도 |
|---|---|---|
| `local` | `~/.claude.json` (프로젝트 경로) | 개인용, 현재 프로젝트만 |
| `project` | `.mcp.json` (프로젝트 루트) | 팀 공유, 버전 관리 |
| `user` | `~/.claude.json` | 전역, 모든 프로젝트 |

### MCP 서버 관리 명령어

```bash
claude mcp list          # 설치된 MCP 서버 목록 확인
claude mcp get github    # 특정 서버 상세 정보 확인
claude mcp remove github # MCP 서버 제거
/mcp                     # 클로드 코드 내 서버 상태 확인
```

---

## 3.7.2 필수 MCP 서버

| MCP 서버 | 용도 |
|---|---|
| **GitHub** | PR 생성, 이슈 관리, 코드 리뷰 자동화 |
| **Context7** | 최신 라이브러리 문서 실시간 조회 → 할루시네이션 방지 |
| **LSP** | 심볼 탐색 토큰 효율 최대 수십 배 향상 |
| **PostgreSQL** | 자연어로 DB 쿼리 실행 |
| **Sentry** | 에러 모니터링·디버깅 |

### LSP 토큰 효율 비교 (그림 3-2)

```
LSP 없음: grep → 847개 매치 → 파일 반복 Read → 정답 추론  (~8,000 tok)
LSP 있음: goToDefinition → AST 즉시 조회 → 파일명+줄 번호  (~100 tok)
```

> LSP는 MCP가 아니라 **플러그인** 형태 → `/plugin` 커맨드로 설치

```bash
/plugin marketplace add Piebald-AI/claude-code-lsps
/plugin install vtsls@claude-code-lsps
```

### 보안 주의사항
- 비공식 MCP 서버는 검증 안 된 보안 위험 존재
- API 키/토큰은 환경 변수로 관리, 코드에 직접 노출 금지
- MCP 출력 토큰 기본 제한 1만. `MAX_MCP_OUTPUT_TOKENS`로 조절 가능

## 3.7.3 확장 기능 사용의 원칙

**핵심: 많이 설정한다고 좋은 것이 아니다**

| 문제 | 설명 |
|---|---|
| 토큰 낭비 | 미사용 MCP도 도구 정의가 컨텍스트에 추가됨 |
| 응답 지연 | 서버 많을수록 초기화 시간 증가 |
| 의도치 않은 동작 | 도구 충돌, AI의 잘못된 도구 선택 |
| 디버깅 어려움 | 문제 원인 파악 난항 |

### 권장 접근법 — 필요할 때 필요한 것만

```
① CLAUDE.md + 필수 Hook만 기본 설정
② MCP는 작업할 때만 추가 (GitHub 작업 시 GitHub MCP)
③ 사용 후 /mcp 명령으로 불필요한 서버 비활성화
④ --scope local로 프로젝트별 분리
```

### 작업 유형별 도구 선택 가이드

| 작업 유형 | MCP | Hook | Skill |
|---|---|---|---|
| 깃허브 PR/이슈 | GitHub | - | - |
| DB 작업 | PostgreSQL | - | - |
| 최신 라이브러리 사용 | Context7 | - | - |
| 코드 품질 관리 | - | pre-commit: lint | - |
| TDD 워크플로 | - | post-edit: test | 테스트 작성 가이드 |
| 팀 협업 | Slack | post-commit: 알림 | 코드 리뷰 체크리스트 |
| 문서 작성 | - | - | API 문서 템플릿 |
| 디자인 연동 | Figma | - | 컴포넌트 명세 템플릿 |

> **핵심 원칙:** 도구는 문제를 해결하기 위해 존재한다. 작업에 맞는 최소한의 설정으로 시작하고, 필요에 따라 점진적으로 확장하는 것이 클로드 코드를 효과적으로 활용하는 방법이다.
