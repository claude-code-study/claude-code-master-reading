### 3.1  Garbage In, Garbage Out

* AI는 코드를 빠르게 생성하지만, 그 코드가 올바른 방향인지는 보장하지 못한다.
* 잘못된 방향으로 코드가 작성되기 시작하면 무한 수정과 유지보수 지옥에 빠질 가능성이 높다. 
* **핵심:** AI와 협업할 때는 **'설계'**가 가장 중요하다. AI는 '어떻게(How)' 구현할지는 잘 알지만, '무엇을(What)' 만들어야 하는지는 모른다. 따라서 간단명료한 명세의 **마크다운 문서**가 필요하다.


### 3.2 작은 단위로 쪼개기의 힘

> 💡 **Tip:** 설계 단계에서 마크다운 파일을 만들 때, 여러 가지 AI 에이전트를 교차 활용하면 비용을 줄이고 품질을 높일 수 있다.
> 1. **토큰 절감:** 컨텍스트가 작아져 비용이 줄어든다.
> 2. **교차 검증:** 다양한 모델의 시각으로 더 최적화된 결과를 얻는다.

### 3.2.1 한 번에 하나의 작업만 요청하기
* 기능을 잘게 쪼개고, AI에게 단일 작업만 요구해야 한다.
* 결과물이 명확해지고 작업 단위가 작아져 **검증이 쉽고, 에러 발생 시 빠른 피드백**이 가능하다.

### 3.2.2. 작업 분해의 기준과 단위
* **단일 책임 원칙(SRP) 적용:** 하나의 요청은 하나의 책임만 다뤄야 한다.
* **테스트 가능한 단위:** 결과물을 독립적으로 테스트할 수 있어야 한다.
* **시간 기준:** 10분 내에 검증 가능한 크기여야 한다.
* **경계 설정:** 파일 혹은 기능 단위의 경계를 명확히 하여, 각 기능이 책임 범위를 넘지 않도록 한다.

### 3.4 매 단계 리뷰하기: 주의 깊은 수정의 원칙
### 3.4.1 리뷰해야 할 것들
* 요구사항 충족 여부
* 코드 품질 (가독성, 효율성 등)
* 의도치 않은 변경(사이드 이펙트) 발생 여부

### 3.4.2 단계별 리뷰 습관 만들기
* **작은 작업 = 작은 리뷰:** 코드 양이 적을 때 검토해야 지치지 않는다.
* **테스트 먼저:** 코드를 합치기 전에 테스트 코드를 먼저 돌려본다.
* **실행 및 질문:** 무조건 승인하기 전에 실제로 실행해보고, 의심스러운 부분은 AI에게 다시 질문한다.

### 3.6 증강코딩과 TDD - AI 시대의 개발 방식
### 3.6.1 증강코딩: AI 시대의 새로운 개발 방식
* TDD의 창시자 '켄트 백(Kent Beck)'이 제안한 개념.
* 단순히 AI가 코드를 대신 짜주는 것을 넘어, **개발자가 AI와 협업하여 '깔끔하게 동작하는 코드'를 만들어가는 방식**을 의미한다.
* 개발자는 코드 품질, 복잡도, 테스트 커버리지 등의 가치 체계를 그대로 유지하고, AI는 '타이핑'과 '초안 작성'을 대신할 뿐이다.

### 3.6.4 AI가 만드는 회귀 방지하기
* **회귀 현상:** 소프트웨어가 변경된 후, 이전에 정상 동작하던 기능이 갑자기 동작하지 않는 현상.
* AI가 기존 코드를 수정하면서 엉뚱한 곳을 건드리지 않도록, **단단한 테스트 코드(TDD)** 기반의 회귀 방지 장치가 필수적이다.
