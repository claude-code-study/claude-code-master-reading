# CHAPTER 4 핵심 정리

## 4. 프로젝트 소개와 요건 정의

4장에서는 단순히 TODO 앱을 구현하는 방법보다,  
AI와 함께 실제 서비스를 개발하기 전에 요구사항과 구조를 어떻게 설계해야 하는지에 초점을 맞춘다.

주요 흐름은 다음과 같다.

- 기술 스택 선정
- 요구사항 정의
- 명세 문서 작성
- TDD 기반 설계
- SDD(Spec-Driven Development) 이해

---

## 4.1 TODO 앱으로 배우는 풀스택 개발

TODO 앱은 간단해 보이지만 실제 서비스 개발에서 자주 사용하는 핵심 개념이 대부분 포함된 예제다.

포함되는 개념:
- CRUD(Create, Read, Update, Delete)
- 상태 관리
- API 통신
- 데이터 저장
- 테스트
- 배포 흐름

즉, 작은 규모의 프로젝트라도 풀스택 개발 흐름 전체를 경험할 수 있다.

### 4.1.1 프런트엔드: React + TypeScript

프런트엔드는 React와 TypeScript 기반으로 구성한다.

선택 이유:
- 컴포넌트 기반 개발 가능
- 유지보수성 향상
- TypeScript를 통한 타입 안정성 확보
- AI와 협업 시 명확한 타입 정보 제공 가능

특히 TypeScript는 AI가 코드 구조를 이해하는 데에도 도움이 된다.

### 4.1.2 백엔드: Node.js + Express / Next.js API Routes

백엔드는 다음 두 가지 방식 중 상황에 맞게 선택할 수 있다.

#### Express
- 전통적인 Node.js 서버 구조
- 높은 자유도
- 직접 구조 설계 가능

#### Next.js API Routes
- 프런트/백엔드를 하나의 프로젝트에서 관리 가능
- 비교적 단순한 설정
- 빠른 MVP 개발에 유리

책에서는 소규모 프로젝트나 초기 서비스 단계에서는 Next.js API Routes 방식이 생산성이 높다고 본다.

### 4.1.3 데이터베이스 선택

데이터베이스 선택 시 고려할 요소:
- 프로젝트 규모
- 데이터 구조 복잡도
- 유지보수 난이도
- AI와의 협업 편의성

예시:
- SQLite → 소규모/학습용
- PostgreSQL → 실무형 프로젝트
- MongoDB → 유연한 스키마 구조

이 장에서는 이후 실습을 위해 PostgreSQL 사용 흐름도 함께 다룬다.

## 4.2 요구사항 정의하기

구현 전에 요구사항을 명확하게 정의하는 과정이 중요하다.

특히 AI를 활용할수록 요구사항의 명확성이 결과물 품질에 직접적인 영향을 준다.

### 4.2.1 기능 요구사항 정의

“무엇을 해야 하는가”에 대한 요구사항이다.

예시:
- TODO 생성
- TODO 수정
- TODO 삭제
- 완료 여부 변경
- 목록 조회

### 4.2.2 비기능 요구사항 정의

“어떻게 동작해야 하는가”에 대한 요구사항이다.

예시:
- 빠른 응답 속도
- 모바일 대응
- 안정성
- 유지보수성
- 테스트 가능 구조

실무에서는 기능 구현만큼 비기능 요구사항도 중요하다.

### 4.2.3 사용자 스토리 정의

사용자 관점에서 기능을 서술하는 방식이다.

예시:

> 사용자는 해야 할 일을 추가할 수 있다.  
> 사용자는 완료된 일을 체크할 수 있다.

사용자 중심으로 요구사항을 정리하면:
- 기능 우선순위 판단이 쉬워지고
- AI에게 더 명확한 컨텍스트를 전달할 수 있다.

## 4.3 클로드 코드와 함께 요건 문서 작성하기

이 장에서는 AI와 협업하기 위한 문서화의 중요성을 강조한다.

핵심은 다음과 같다.

> AI에게도 명확한 설계 문서가 필요하다.

### 4.3.1 프로젝트 구조 및 실제 개발 계획 수립하기

구현 전에 아래 내용을 먼저 정리한다.

- 디렉터리 구조
- 기술 스택
- 개발 순서
- API 구조
- 데이터 흐름
- 테스트 전략

초기 구조 설계는 프로젝트 유지보수성과 생산성에 큰 영향을 준다.

### 4.3.2 PRD, TRD, REQUIREMENTS.md 작성

참고:
- https://github.com/claude-code-expert/example/tree/main/docs

#### PRD(Product Requirements Document)

서비스 요구사항 문서
- 제품이 '무엇을' 하는 지를 정의하는 문서

포함 내용:
- 기능 설명
- 사용자 요구사항
- 서비스 목적

#### TRD(Technical Requirements Document)

기술 설계 문서
- '어떻게' 구현할지 기술적으로 명세

포함 내용:
- 시스템 아키텍처
- 디렉터리 구조
- 데이터 흐름
- 성능 기준
- 보안 등

#### REQUIREMENTS.md

실제 개발 시 참고하는 요구사항 명세

Claude와 협업할 때:
- 역할 정의
- 코딩 규칙
- 프로젝트 구조
- 구현 범위

등을 함께 정리하면 더 안정적인 결과를 얻을 수 있다.

## 4.4 명세서 설계와 TDD 방식으로 개발 시작하기

이 장에서는 구현 전에 “설계와 테스트”를 먼저 정의하는 흐름을 소개한다.

### 4.4.1 데이터 설계(DATA_MODEL.md)

먼저 데이터 구조를 정의한다. 

예시:
- TODO id
- title
- completed
- createdAt

데이터 구조가 명확해야:
- API 설계
- DB 설계
- 타입 정의

까지 일관성 있게 이어질 수 있다.

- 
 
### 4.4.2 API 설계 (API_SPEC.md)

프런트엔드와 백엔드 간 통신 규칙을 정의한다.

예시:
- GET /todos
- POST /todos
- PATCH /todos/:id
- DELETE /todos/:id

API 명세를 먼저 정의하면 AI도 더 안정적으로 구현할 수 있다.

### 4.4.3 컴포넌트 및 UseCase 설계 (COMPONENTS_SPEC.md)

기능을 단위별로 나누어 설계한다.

예시:
- TodoInput
- TodoList
- TodoItem

UseCase 단위로 분리하면:
- 유지보수성 향상
- 테스트 용이성 증가
- AI 코드 생성 품질 향상

효과를 얻을 수 있다.

### 4.4.4 테스트 케이스 정의

구현 전에 테스트 기준을 먼저 작성한다.

예시:
- TODO 생성 시 목록에 추가되는가
- 빈 값 입력 시 에러가 발생하는가
- 삭제 후 목록에서 제거되는가

### 4.4.5 TDD 방식의 개발 흐름

TDD(Test Driven Development)의 기본 흐름:

1. 실패하는 테스트 작성
2. 최소한의 코드 구현
3. 테스트 통과
4. 리팩터링

AI와 함께 개발할 때도 TDD는 코드 품질 유지에 도움이 된다.

### 4.4.6 PostgreSQL 설치

실습에서는 PostgreSQL 설치 및 연결 흐름도 다룬다.

핵심 포인트:
- 실무에서 많이 사용하는 관계형 데이터베이스
- 안정적인 데이터 관리 가능
- Prisma 등 ORM과 함께 사용하기 좋음

### 4.4.7 TDD로 개발 시작하기

실제 개발 흐름은 다음 순서로 진행된다.

1. 요구사항 정의
2. 테스트 작성
3. 최소 구현
4. 리팩터링
5. 반복 개선

즉:

> “명세 → 테스트 → 구현”

흐름을 기반으로 개발을 진행한다.

## 4.5 SDD와 Spec Kit

4장 후반부에서는 AI 시대에 맞춘 개발 방식인 SDD 개념을 소개한다.

### 4.5.1 SDD란 무엇인가

SDD(Spec-Driven Development)는:

> “명세 중심 개발”

방식이다.

코드보다 먼저:
- 요구사항
- 구조
- API
- 데이터 모델
- 테스트 기준

등을 명확하게 정의한다.

### 4.5.2 왜 AI와 SDD가 잘 맞는가

AI는 명세가 명확할수록 더 정확하게 동작한다.

즉:
- 애매한 요청 → 불안정한 결과
- 명확한 명세 → 안정적인 결과

로 이어진다.

### 4.5.3 TDD와 SDD의 결합

SDD와 TDD를 함께 사용하면:
- 설계 품질 향상
- 테스트 안정성 확보
- AI 협업 효율 증가

효과를 얻을 수 있다.

흐름:
1. 명세 작성(SDD)
2. 테스트 정의(TDD)
3. 구현
4. 개선

### 4.5.4 Spec Kit으로 SDD 워크플로 자동화하기

Spec Kit은:
- 요구사항 정리
- 명세 문서 생성
- 구조 정의

등을 자동화하는 도구로 소개된다.

특히 AI와 함께 사용할 때:
- 일관된 문서 구조 유지
- 개발 흐름 표준화
- 컨텍스트 관리

에 도움이 된다.

### 4.5.5 수동 워크플로 vs Spec Kit

#### 수동 워크플로

장점:
- 높은 자유도
- 작은 프로젝트에 적합

단점:
- 문서 누락 가능성
- 일관성 유지 어려움

#### Spec Kit 사용

장점:
- 구조 표준화 가능
- AI 협업 효율 증가
- 문서 품질 유지

단점:
- 초기 학습 비용 존재
- 작은 프로젝트에는 다소 과할 수 있음

### 4.5.6 실무 활용 팁

책에서 강조하는 핵심은 다음과 같다.

- AI에게는 명확한 컨텍스트 제공이 중요하다.
- 구현 전에 설계와 명세를 먼저 정의해야 한다.
- 작은 프로젝트라도 구조를 먼저 잡는 습관이 중요하다.
- TDD와 SDD를 함께 사용하면 유지보수성이 높아진다.
- AI는 개발자를 대체하는 존재가 아니라 협업 도구에 가깝다.
